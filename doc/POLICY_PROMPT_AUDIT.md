## 结论

原有中文分区、字段和动作列表可以继续使用。优先级应是：实体与动作对应明确 → 关键公开信息不丢失 → 数值和规则语义准确 → 条件去重和精简。更换格式本身不能解决这些问题。

当前并非“所有可见信息都完整给到了模型”：基础状态、实体说明、Boss名称、牌组、当前房间历史等已有覆盖，但若干运行时字段、升级预览和牌堆明细仍存在缺口。另一方面，原始描述、来源标记和重复字段确实占了可观篇幅。

不能从这些发现直接推断某次错误动作由提示词造成，也不能保证精简后游戏成绩会提高。下文区分源码确认、真实日志确认和构造示例。

## 1. 优先修复：动作与实体的对应

源码位置：[动作生成](../sts_agent/runtime/controller.py) 1657—1679、[API别名投影](../sts_agent/policy/api.py) 153—157、[实体渲染](../sts_agent/policy/local_qwen.py) 276—328。

当前手牌用无显式位置的列表显示，动作标签只有名称与目标。API再将内部动作转换成 `A<n> + label`，没有把 `card_index` 一同呈现。不可打出的牌还会被跳过，因此 `A1` 不一定对应手牌1。

真实请求165中，A1和A5都是“出牌 打击 -> 敌人 0”，分别对应 `PLAY 1 0` 和 `PLAY 5 0`。这批重复牌的可见属性相同，不能据此声称发生了有害误选。对全部2,224次请求的补充扫描也未发现同名手牌具有不同整行属性的实例。

但离线构造“手牌1不可打出、手牌2免费、手牌3正常费用”后，现有链路会生成：

```text
手牌列表：
- 打击，可打出=否，本回合费用=1
- 打击，可打出=是，本回合费用=0
- 打击，可打出=是，本回合费用=1

合法动作：
- A1：出牌 打击 -> 敌人 0       实际为 PLAY 2 0
- A2：出牌 打击 -> 敌人 0       实际为 PLAY 3 0
- A3：结束回合
```

上面“实际为”仅用于开发者审查，当前模型没有看到。模型只能依赖未明确声明的遍历顺序来对应实例。

建议仍使用现有A别名，仅补足位置：

```text
【手牌】
- 手牌2：打击，本回合0费，当前牌面单段伤害6。
- 手牌3：打击，本回合1费，当前牌面单段伤害6。

【合法动作】
- A1：打出手牌2 打击 -> 敌人0。
- A2：打出手牌3 打击 -> 敌人0。
```

同样检查敌人序号、药水栏位、网格/手牌选择位置、奖励短编号的对应。不能因为显示文字相同就合并原本独立的合法动作，也不需要把UUID重新暴露给模型。

## 2. 采集器已有的有效字段在投影中被丢弃

[卡牌字段白名单](../sts_agent/runtime/controller.py) 453—483和[战斗规范化](../sts_agent/runtime/controller.py) 1603—1614，没有完整接收相邻ActionRecorder仓库 `RuntimeStateFields.java` 已提供的公开字段。

- 卡牌有 `free_to_play_once`、`exhaust_on_use_once`、`is_innate` 等。当前白名单未接收前两项，先天字段则使用不同名称 `innate`。
- 采集器还提供每回合能量、手牌数量相关字段和本回合出牌数，玩家投影主要保留当前HP、格挡、能量、姿态和Power。
- 牌组汇总进一步只保留ID、名称、类型、费用、升级次数、描述和词条；某些实例差异可能在这里丢失。

建议按决策用途逐项核对，而不是把所有原始字段都塞回来。例如“本次免费打出”应和有效费用一起明确表达，不能只让模型看到牌面费用1、当前能量0，再从合法动作反猜其可用原因。

这属于当前源码确认的信息通路缺口。本批旧日志不能量化它对成绩的影响；本次也未实机确认所有新增字段在每种场景均已成功输出。应以真实消息和游戏对象语义验证后再接入。

## 3. 升级选择缺少升级后的效果

真实请求245/250/279的升级候选只有当前未升级说明；请求246/251/280的确认页中，待确认实体更只有ID/名称，多个效果字段显示未知。

[选牌投影](../sts_agent/runtime/controller.py) 1480—1512没有升级前后预览的表达通路。单靠“比较升级对费用、效果和牌组需求的改善”这句提示，不能让模型知道缺失的升级效果。

建议读取游戏公开的升级预览，标清当前效果与升级后效果。不要对游戏中的原对象直接调用升级来造说明；无法取得时保持未知，并保留选牌来源和已选对象。已有日志中没记录的预览也不能凭空补齐。

## 4. 数值含义应先于精简

[数值复制](../sts_agent/runtime/controller.py) 552—570与[字段标签](../sts_agent/policy/local_qwen.py) 145—151存在语义不一致：`final_single_hit_damage` 被展示为“最终单段伤害”，实际使用的是游戏手牌缓存值，未按各目标统一计算最终扣血。

建议改为“当前牌面单段伤害”“当前牌面格挡”，说明我方效果通常已计入缓存，不再次叠加力量/虚弱；目标格挡和Power仍由模型结合判断。继续保留段数，不把单段值当作总伤害。

其他需要明确的数值：

- `cost=-1` 应按游戏费用语义显示X费；不要当成负费用。基础费用与本回合费用不同时，两者都保留。
- `Energy Energy` 等来自上游将能量图标转换为英文字符串。只对有明确语义的图标进行规范化，避免模型自行数词或把图标当普通文字。
- 牌组/奖励卡牌的伤害缓存可能尚未初始化。不能统一删除基础数值，也不能把缓存中的哨兵值当作真实负伤害。
- `can_use / target / is_playable` 应有明确中文语义；未知、否、0不能合并。目标要求为否，不意味着药水不能使用。

## 5. 不擅自固定终局目标；权衡生存与成长

原审查建议用实验配置指定第三幕Boss或心脏目标。2026-10-19复核后撤回：这不是本次提示词优化应擅自加入的任务约束。
当前通用开头只说明正在游玩，不固定终局目标，也不保留为此新加的专用配置。

钥匙区提供游戏规则：集齐红、绿、蓝三把钥匙，才能在击败第三幕Boss后进入第四幕。进入第四幕的条件与要求每局都收集钥匙不是一回事。

“优先存活”也不宜解释成每步机械最大化即时HP。生命是可以合理支付的资源；精英、事件、升级和输出有时值得承担短期掉血。保留生存、成长、资源的权衡，以及战斗中避免无收益空过和适时使用药水的简短提示。这里是策略措辞风险，不是已证明的失败原因。

## 6. 历史防重提醒过宽，并重复出现

[通用开头](../sts_agent/policy/local_qwen.py) 436写“历史动作已执行，不要重复提交”；[历史说明](../sts_agent/policy/local_qwen.py) 350又说明取消/未执行的尝试不生效。

同名牌可以连续打，后续回合可以再打相同牌，翻牌事件可能需要重新翻已知位置，商店也可以合法重入。提示应防止模型把历史当成待执行指令，而不是笼统禁止再次选择相同动作。

建议只保留一次范围准确的说明，例如：

```text
房间历史记录过去的操作；取消或未执行的尝试不产生效果。
根据当前状态与合法动作决定下一步，允许游戏规则支持的再次操作。
```

历史继续保留当前房间最近30步、实际对象和目标、用途/来源、确认/返回语义以及执行状态。不重新加入 `observed_changes / event_changes`，不把过去的A别名当作稳定实体身份。

## 7. 最值得精简的是重复数据

`_entity_line` 最后会遍历所有剩余字段，所以可读描述与原始描述、固定来源、完整性标记、零值和false标志一起出现。

真实输入中，展开后的 `description` 没发现未解析的 `!D! / !B! / !M!`；这些模板占位符位于 `raw_description`。不能把“模型同时看到两套文本”说成“可读描述已经解析失败”。

建议按条件处理：

| 内容 | 建议 |
| --- | --- |
| 完整可读描述与相同raw原文 | 展示一次完整效果；raw保留在审计日志 |
| 固定 `description_source=game_runtime` | 留在审计层 |
| 说明完整且已成功展开 | 不反复打印“完整=是” |
| 说明确实不完整或变量未解析 | 明确告知模型，不当成完整知识 |
| 空药水槽的名称、描述、来源等 | 合并为容量和空槽数；保留真实药水栏位 |
| 相同HP、相同基础/当前费用、相同伤害/最终伤害 | 有条件去重，不删数值差异 |
| 空界面章节、空本局记忆、零历史说明 | 条件省略或短写 |
| 当前事件选项在多个区块逐字重复 | 以一个明确的当前选项表为准，保留必要开场历史 |
| 已知false的虚无/保留等标志 | 可按展示约定省略；真和未知须正确区分 |

上述精简维持原有中文分区形式。实体效果、词条解释、目标状态和必要流程来源不因“文本长”而整块删除。尤其不能删除所有牌组描述、Power、事件开场文本或翻牌记忆，再假定预训练模型自然知道。

## 8. 不应混为一谈的信息取舍

完整地图仅在MAP输入已符合当前约定，建议保持。非地图不带全图可以降低重复，但这也意味着非地图场景不能假装拥有完整的未来路线信息。

当前模型只有抽牌堆、弃牌堆、消耗牌堆数量。完整永久牌组并不能代替这些牌堆的逐张内容，尤其对消耗、弃牌检索和回收卡牌的决策。是否增加公开牌堆明细应作为单独的信息量实验；不能只称其为格式精简，也不应暴露隐藏抽牌顺序。

对于当前A0铁甲战士基线已经较完整的场景处理，应继续保留：战斗内生成选牌与永久卡牌奖励分开、锻造/删除/变化用途、当前已选牌与确认阶段、奖励短编号和互斥关系、Boss名称、钥匙三态、公开事件棋盘以及取消尝试。

## 外部实现对照

### Orak：参考结构和明确索引，不能照搬任务范围

Orak把稳定角色/规则与动态状态分开组织；实际状态渲染给手牌、敌人和奖励卡牌明确编号。它们是对本项目最直接的参考点。保留原有中文分区也能做到，不需要先切换Markdown。

其零样本模板还要求显式推理，并允许一次输出多条命令；公开环境主要把战斗与卡牌奖励交给模型。这些与本项目的低延迟单A输出、完整局操作范围不同，不能整段照搬或直接归因其成绩更优。规则文本也有简化，例如“只有攻击意图才造成伤害”无法覆盖锋利外壳等效果。

### 其他StS项目：借鉴接口，不视为提示词效果的证据

- [sts-bench](https://github.com/alavico/sts-bench)：采用简短状态摘要、按需观察工具和单个typed action；默认保留本层会话。这支持检查动作类型、状态摘要和房间上下文的组织，但增加检索工具会改变当前单次决策接口，需要单独实验。
- [Spire Agent的LLM实现](https://github.com/AttemorySystem/spire-agent/blob/main/src/spire_agent/tools/llm_agents.py)：显式规定命令索引与作用范围，保留上次命令的确认/错误信息。可以参考对应关系；其命令加理由、领域工具和多组件结构不等同于本项目的单模型单A接口，不能把项目自报胜绩当作单段prompt的效果。

格式研究也没有给出“Markdown普遍优于原格式”的结论。不同模型和任务会对语义等价的格式变化敏感，应保留当前默认，后续独立对比：[Sclar等人的格式敏感性研究](https://arxiv.org/abs/2310.11324)、[不同提示格式对比研究](https://arxiv.org/abs/2411.10541)。这些研究不是对当前Qwen/StS设置的直接验证。

## 建议的实施顺序与验收

1. 保持 `plain_text / canonical`，先修动作位置对应和有用运行时字段的投影；补上公开升级预览的可靠通路。
2. 不额外固定终局目标；调整伤害和历史防重等措辞，统一费用和能量的含义。
3. 条件去重原始描述、固定来源、空槽、重复值和空章节；保留必要的未知/不完整提示。
4. 从同一批真实状态重新生成输入，审查战斗、奖励、商店、事件、营火和各类二级选牌；保证API推理、SFT导出和评分使用同一构造器。
5. 离线检查动作引用一一对应、公开事实不丢失、不引入隐藏信息；重新测token分布。然后在冻结的10个种子上做配对评测，报告进度分、终局、格式错误、技术中止、token和延迟。

只改措辞和展示时，不同时调整温度、思考模式、模型权重或自动规则，以便识别改动影响。10个种子仍只够初步对照，不能将一两局改善解释成稳定显著提升。

可审阅的通用开头方向（仅示例）：

```text
你正在游玩《杀戮尖塔》。
根据当前状态选择下一步，权衡当前生存、牌组成长和资源收益。
只输出当前合法动作中的一个动作ID，例如A2。
```
