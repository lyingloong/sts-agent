# 模型输入、房间历史与动作空间

本文对应当前 `baseline_inference`、本地策略和人工轨迹 SFT 的共享状态投影。
默认原格式的完整拼接示例见 [POLICY_PROMPT_PREVIEW.md](POLICY_PROMPT_PREVIEW.md)，
待开发的 Markdown 格式方案见 [POLICY_PROMPT_PREVIEW_MARKDOWN.md](POLICY_PROMPT_PREVIEW_MARKDOWN.md)。
模型看到的是公开游戏信息，不是原始 CommunicationMod 消息的所有字段。

## 1. 一次决策输入的组成

基线单动作 API 通过 `policy.api.prompt_format` 选择输入格式：

- `plain_text`：默认值，已实现；使用原有中文字段标签、分区、缩进和自然语言动作说明。
- `markdown`：与原格式并列的可选方案，目前待开发，尚未实现 renderer；显式选择时配置校验会报错。

这项配置仅作用于基线单动作 API；本地策略、教师和 RL 的配置接口不在此范围。

官方权重基线的 `canonical` 输入顺序为：

1. 玩家身份和默认回合规则；不额外固定终局目标。
2. 只输出本次单个合法动作别名的格式要求。
3. 当前场景提示：战斗、地图、商店、事件、选牌、奖励等。
4. 当前公开状态：全局变量、牌组、遗物、药水、当前场景内容。
5. 当前房间历史：精简的动作语义、选牌用途和流程记录，不包含前后状态变化。
6. 本次合法动作别名表和最终输出提示。

状态和历史使用中文字段标签、分区、缩进和自然语言动作说明，不向该基线要求 JSON 输出。
底层仍是结构化 observation，便于审计、回放和使用相同内容生成 SFT。
`policy.api.prompt_template` 的 `canonical`、`state_first`、`decision_first` 仅选择区块顺序，
不选择输入格式，也不改变可见信息。

### 实体效果字段

实体信息来自游戏运行时对象；不加载静态知识库或经验文件。

- 卡牌核心字段：`id/name/type/cost/cost_for_turn/upgrades/is_playable/description`。
  源提供时还保留描述来源/完整性标记、`target`、伤害/格挡及基础值、
  `magic_number/hit_count/multi_damage`、颜色/稀有度和消耗、虚无、保留等标志。
  另接入 `free_to_play_once/exhaust_on_use_once/is_innate`、费用修改和瓶装指定等已公开标志。
  升级GRID候选和待确认牌可含上游 `upgrade_preview`、来源与可用状态；未取得预览时不按名称补写。
  战斗手牌的 `final_single_hit_damage/final_block` 使用实时牌面缓存值，
  不在 Python 中重复叠加力量、虚弱等效果；单段值不代表多段总伤害，也不保证对每个目标都是最终扣血值。
  完整实时描述已展开这些效果时，正文不再重复展示伤害/格挡、基础值、效果参数或段数；这些字段仍完整保留在结构化观察和原始记录中。
  说明不完整、完整性显式未知、存在未解析变量或raw另有独有效果时，保留数值兜底。
  费用与不同的本回合费用、未写入描述的实例属性继续展示；X费用显示为X而不是-1。
  多目标差异值只有在能可靠对应当前敌人序号时，才转为 `target_damage` 的逐目标单段伤害，不把数组当成攻击段数。
- 药水：`id/name/description/target/can_use`，以及源提供的原始描述、来源、tooltips。
- 遗物：`id/name/description`，以及源提供的原始描述、来源、非负计数器。
- Power：`id/name/amount/type` 和源提供的运行时描述、来源、完整性标记。
- 玩家：除当前能量外，接收源提供的基础/当前每回合能量补充基数、抽牌基数、本回合出牌数；它们不等于当前可用能量或手牌上限。
- 伤害意图：单段实时伤害、段数、乘积得到的总意图伤害；未取得时为 `null`。
  持有符文圆顶时不提供敌人意图。

结构化状态和原始审计字段继续完整保留。文字渲染通过独立展示副本去除重复说明和来源、已被完整描述覆盖的数值参数、重复费用与已确认false的可省略属性，
空药水槽合并为栏位数/空槽数，不再整块重复空槽说明。未知值、不完整效果和有意义的差异仍展示。
`potion_slot_count` 按源药水数组长度确定，数组包含空槽；缺失或null与真实空数组不同。预览模拟A0战士的三个空槽，不使用空数组代替。
`is_playable` 的文字展示仅用于当前战斗手牌，不把永久牌组或选牌/升级预览上的缓存误解为当下能否出牌。
本房间商人是否曾打开可保留为流程事实；全局访问商店/跳过奖励的坐标列表不再进入文字正文。
`action_phase` 供流程就绪/调度使用，仍保留在结构化状态，但不展示给动作模型。
原始 `choices` 仍保留作动作映射，但文字中不单列【当前选择】；可执行选项由【合法动作】统一列出，场景内选项说明不因此删除。
历史事件开场中，choices与详细options明确重复的内容也去重；未被详细选项覆盖的历史内容保留为“当时可选项”。选项的正文、效果、代价和禁用状态不删除。
钥匙区补充说明：集齐红、绿、蓝三把钥匙，才能在击败第三幕Boss后进入第四幕；这不是要求每局必须收集钥匙的策略指令。

手牌 `card_index` 从1开始，敌人 `monster_index`、库存药水 `slot`、选择 `choice_index` 从0开始。
索引在过滤前按原始列表确定；已选/确认对象仅按显式位置或唯一实例标识关联，不凭同名猜测。
商店商品列表顺序不代表CHOOSE顺序；原始合法动作的索引和编号保持不变。
GRID确认页保留完整待确认对象与升级预览，但不把空 `choice_list` 中的卡牌编号伪装成可执行的选择位置。

### 公开牌堆明细

`combat.draw_pile/discard_pile/exhaust_pile` 按完整公开属性归并计数并确定性排序，排除UUID和位置，不保留源数组的引擎顺序。
结构化投影保留卡牌ID、名称、升级、费用、说明、基础数值和实例属性；文字以完整描述为主，必要时才显示数值兜底。不把非手牌的可打出标志或临时目标伤害/格挡缓存当作未来出牌数值。
数量仍由源列表长度确定；未提供明细为null，已知空为[]。部分项缺失时保留已知实体，并用 `*_pile_missing_count` 标明未知项数，不生成虚构卡牌。
三堆随整个战斗状态在战斗内选牌时保留，非战斗时移除残留。

### 运行时词条解释与实体标识

Recorder 在卡牌、药水、遗物和 Power 上提供 `keyword_tooltips`（`header/body`）。
卡牌说明通过其 `keywords` 查询游戏当前语言的 `GameDictionary`，药水/遗物读取实际关联 tooltip；
Power 的机制直接由对象自身 `description` 提供，不按名字匹配其他同名词条。
不使用静态知识库，不为游戏未提供的词条猜测解释。下游仅收集当前可见实体涉及的词条，
按名称和说明正文一起去重为 `keyword_explanations`，在 prompt 的【词条解释】区统一显示，
同名但含义不同的真实说明不会相互覆盖。
牌组中的牌也属于可见实体；未公开牌面不参与收集，历史动作不重复附上词条。
普通房间会先移除上一战斗残留的 combat，再收集词条。旧日志未记录的解释不能凭空补齐。

`Strike_R`、`SpeedPotion` 等**种类 ID**仍保留。实例 UUID、状态/事务 ID 不向模型展示，
但完整保留在原始状态/轨迹和控制链路中。新版 Recorder 的奖励同时提供 `reward_ref`（例如 `R1`）：
同一奖励对象在本采集片段中保持相同编号，领取、跳过、重开界面或列表缩短不会重新编号。
结构化观察仍可用 `reward_id/linked_reward_id/source_reward_id` 的短别名进行内部关联。
最终模型正文和动作历史不再显示奖励编号；展示副本在移除编号前，先把公开互斥关系转换成奖励名称/类型及已提供的位置说明。
例如“蓝宝石钥匙与遗物：锚二选一，领取其中一项会放弃另一项”。关联目标缺失或身份冲突时不猜名称，只保留已知的关联互斥性质。
新局/读档片段会重建编号，不能用 `R1` 跨对局或跨读档片段匹配原始数据。
旧轨迹没有 `reward_ref` 时，按该 observation 的历史与当前奖励生成一致的短别名，
只保证本次输入内的关联，不能承诺旧数据的编号在所有历史窗口之间恒定。
卡牌实例通常通过手牌/选择列表位置、名称和升级状态区分，不给模型随机 UUID。

抽牌堆、弃牌堆、消耗牌堆已提供公开卡牌组成及数量，详见上文“公开牌堆明细”。
模型也不接收种子、RNG 状态、隐藏抽牌顺序或尚未翻开的牌面。

### 营火选项说明与活动规则

Recorder 的 `screen_state.rest_option_details` 来自 CommunicationMod 同一可用营火按钮对象
的运行时 `label/description`，不是根据选项名称补造的静态说明。规范化保留每项的
`choice_index/choice/name/description/usable`；原始日志另外保留带格式的 `raw_description`、
`description_source="game_runtime"` 和 `option_class`。
`rest_options` 原字符串和顺序照常保留，`choice_index` 是对应 `CHOOSE` 的 0-based 索引。
`rest_options` 还必须与当前 `choice_list` 全列表的数量、顺序和标识一致；任意错位时
整份说明明细为 `null`，所有营火动作退回原始选项文字，不做部分索引配对。
无法取得或可靠对应列表时明细为 `null`，确认没有选择才为 `[]`；字段缺失保持未知。

模型在【当前界面内容】的“营火选项说明”中读取名称和效果，合法动作在索引及原选项字符串
均匹配时使用游戏本地化名称并附说明，例如 `A1：休息——恢复 24 点生命。`。
这只改变展示文字，动作仍是 `CHOOSE:index=0` / `CHOOSE 0`，编号、命令和操作粒度不变。
游戏未提供名称时使用原选项标识；未提供说明时只显示名称，不凭空补齐效果。
休息描述中的恢复数字及遗物附注是当前按钮实际显示的 UI 说明，
不保证最终净回血；生命上限和遗物 `onRest()` 的额外效果等还可能影响结算。

仅 `REST` 状态附上 `activity_rule`，显示为“营火活动规则”：

> 本次营火只能完成一项营火活动，例如休息、锻造或回忆。完成其中一项后，其余营火活动将不再可选。若活动尚未完成，且界面允许取消返回，则可以重新选择。使用或丢弃药水不计入营火活动。

“进入锻造选牌”本身不等于已经完成锻造，是否可取消或重选仍以当前合法动作为准。
这条规则不改变营火入口、选牌、确认、返回和离开分别决策、分别记录的流程。

## 3. 当前房间历史：`room_history`

这里的“完整”指**当前房间内已收到的动作及其必要操作含义**，不是每一步重新附上
整局所有房间的完整状态。离开过往房间后不再全文注入其历史；进入当前房间的那一步仍保留。
现有代码中房间边界以 `(act, floor)` 标识，界面切换本身不创建新房间：

- EVENT → GRID → 确认 → EVENT：同一房间。
- REST → 锻造选牌 → 确认 → REST：同一房间。
- SHOP_ROOM → SHOP_SCREEN → 星系仪奖励 → SHOP_ROOM：同一房间。
- 战斗 → 战后奖励 → 卡牌奖励：同一战斗房间。

保留规则：

- 所有房间统一保留最近 **30 条**记录，包括战斗奖励、事件和二级选牌。文字中不重复固定窗口、总数和显示数，仅在确有省略时说明省略步数。
- 超过 30 条时省略最早的动作行；当前事件初始说明仍单独提供，翻牌的已公开牌面仍保留在当前棋盘记忆中。
- 不再在底层只保留 16 条；完整房间历史不是从 UI 的六行摘要拼凑出来的。
- 新局清空历史。人工采集收到 `run_resumed` 时重置分段记忆，避免 Save & Load 前被回滚的分支当成当前已经发生的事。
- UI 的 `recent_actions` 使用模型同一份房间历史的最近六条，并调用同一文本渲染器；内容一致，只是条数更少。
- 30 步是显式历史窗口，不是字符串截断。不静默截断字符或丢弃超长样本；如果请求超出服务上下文，明确报错/暂停。
  人工 SFT 导出超出 `--max-length` 时失败。30 步也不保证一定满足模型的 token 容量。
- 历史标题后直接显示动作行，不另加“以下为过去操作”的通用说明；取消、未执行等语义在对应动作行内保留。

历史对象包含：

```text
room: act / floor / room_type
total_steps / shown_steps / omitted_steps / limit（统一为 30）
event_opening: 当前事件最初的公开名称、正文和选项（如有）
steps: 按时间排序的操作记录
```

每条 `steps` 不只是一句“选择 A1”，而是：

- `step_id`、操作前后界面、前后回合、语义动作类型和规范 ID。
- 动作文本；不向模型提供执行来源（模型/人类/控制器自动动作等）。历史不使用易变的 `A1` 别名来代表实体。
- `details`：从动作前状态解析实际操作的卡牌/药水/奖励、敌人目标、选项文本、
  选牌用途/触发来源、奖励 ID、确认或返回时的已选卡牌等。实体仅保留稳定 ID、名称、升级次数和奖励标识；
  敌人目标仅保留索引、ID 和名称，不重复费用、效果描述、价格、伤害、格挡、生命等属性。
- 模型历史不包含 `observed_changes` 和 `event_changes`：不重复展开动作后的资源、
  Power、敌人状态、事件正文/选项等变化。当前资源、敌人和事件阶段由当前状态提供。
- 实际执行状态：排队后取消、跳过执行的尝试明确标注“未执行”，不当作已生效动作。

游戏内快速排队的出牌以已匹配的**执行入口**解析卡牌和上下文，不从下一步手牌倒推动作对象。
自动动作也进入历史，不要求模型再选一次；`environment_auto` 等执行来源仅保留在原始审计记录。
这与“由攻击药水/发现/星盘触发选牌”的**操作触发来源**不同，后者会保留，避免混淆选牌目的。

模型和 UI 使用相同的单行动作语义，例如：

```text
步骤135｜回合1：使用完美打击+ → 敌人0（史莱姆老大）
步骤40：选择事件选项：净化（事件→网格选牌）
步骤41：选择打击用于删除
步骤42：返回（已选牌：打击；用途：删除）
步骤31：翻开位置0（当前位置已公开：痛击）
```

营火锻造、商店删牌仍按入口、选牌、确认/返回分别记录，不合并成已完成动作；
奖励界面区分打开卡牌奖励与领取奖励，并保留奖励 ID。未执行的排队尝试会明确标注。

### 翻牌小游戏

当前棋盘持久保存每个位置是否曾揭示、当前是否翻开、是否已配对、已公开的卡牌。
**牌重新盖回去后，曾公开的牌面仍可见。** 未揭示的牌面一律保持未知。

每次翻牌历史保存稳定位置，并可关联该位置当前已公开的牌面；
尝试次数、配对情况等只在当前棋盘状态提供，不在历史中重复记录其前后变化。
如果动作后快照早于翻牌动画完成，可以从**当前公开棋盘**补上“该位置当前已公开的牌面”，
但不把它谎称为当时快照已确认的最终结果。选择列表索引不等于棋盘位置：优先使用
Recorder 的 `board_position`；在线只在明确的 `cardN` 标签中解析位置，不猜测缺失值。

### 动作后状态的界限

原始轨迹的前后状态仍保留用于复盘和审计；后状态不保证动画全部结束，
也不是严格的单动作因果标签。模型房间历史不包含这类前后状态变化。
当前状态才是下一步决策依据；训练标签仍由动作前状态和实际动作组成，
不使用当前样本动作执行后的状态预测当前样本答案。
后状态未及时提供的中间公开细节无法凭空恢复；因此不能承诺记录了游戏的每一动画帧。

## 4. 动作空间与输出

模型不直接输出鼠标位置、键盘事件或任意命令。controller 将当前 CommunicationMod
允许的操作展开为细粒度语义动作；在基线 API/SFT 中按当前列表顺序赋别名：

```text
【合法动作】
- A1：出牌 打击 -> 敌人 0
- A2：出牌 防御
- A3：结束回合
请输出唯一的动作 ID：
```

模型答案例如 `A2`，由本次别名表映射到 `PLAY:card=2`，再编译为游戏命令。
`A2` **不是**固定的“防御”或固定卡牌：下一状态会重新编号。
输出不允许额外解释/JSON。Candidate Assist 的排序接口和远程教师有各自输出包装，
不要将其包装误当成基线的单动作标签。

| 语义操作 | 规范 ID / 命令示例 | 粒度 |
| --- | --- | --- |
| 出牌 | `PLAY:card=1:target=0` / `PLAY 1 0` | 一张牌和一个敌人目标；无目标牌只一个动作 |
| 结束回合 | `END_TURN` / `END` | 一步 |
| 使用/丢弃药水 | `POTION_USE:slot=0:target=1`、`POTION_DISCARD:slot=0` | 一瓶及需要的目标 |
| 选择选项/卡牌/商品/奖励/节点 | `CHOOSE:index=0` / `CHOOSE 0` | 一次当前界面的选择，不是组合宏动作 |
| 确认或继续 | `CONFIRM` 或 `PROCEED` | 与选牌、进入地图分开记录 |
| 返回/取消/跳过/离开 | `RETURN`、`CANCEL`、`SKIP`、`LEAVE` | 仅当前协议提供且合法时出现 |
| 关闭设置覆盖层 | `KEY:CANCEL` / `KEY Cancel` | 不同时暴露覆盖层下的战斗动作 |

出牌手牌位置是 **1-based**；敌人目标、药水栏位、CHOOSE 索引是 **0-based**。
手牌索引、选择索引、棋盘位置、动作别名是不同概念。

地图不提供药水使用/丢弃动作；地图节点以实际合法选项为准（包括飞鞋规则）。
非战斗场景可丢弃药水，主动使用只开放鲜血药水/果汁；战斗药水按可用性和目标展开。
多选场景只提供尚可选择的实例与合法确认/返回动作。人类原始操作还可能包含取消选中，
采集保留这些细粒度尝试，但最终 SFT 可用性由现有标记决定。

## 5. 实现路径与更新后的数据

- `sts_agent/runtime/controller.py`：规范化、历史入口、状态投影和合法动作。
- `sts_agent/policy/history.py`：原始审计动作解析、精简历史投影、UI/模型共享文本渲染、房间划分和统一 30 步窗口；上限由 `ROOM_HISTORY_LIMIT` 定义。
- `sts_agent/policy/presentation.py`：仅模型输入的词条去重和短标识投影；不修改控制身份和原始轨迹。
- `sts_agent/policy/local_qwen.py`：中文渲染、场景提示、单动作 prompt。
- `sts_agent/policy/api.py`：本次动作别名、远程请求、状态复核和严格解析。
- `sts_agent/recording/trajectory_assembler.py`：人工采集与回放使用相同历史构造。
- `sts_agent/learning/export_human_sft.py`：回放原始 Recorder 数据、生成相同输入的 SFT。
- `sts_agent/commands/preview_policy_prompt.py`：生成文档中的完整示例。

旧的已导出 SFT 文件不会自动变成新历史格式。需要用原始 Recorder 数据重新导出；
原始状态未记录的牌面/说明不能恢复。历史逻辑在本机 controller/bridge 中执行，
远端常驻基线服务只负责推理，不需要为了本次 prompt 改动重新下载模型。

## 6. 指令提交与记录确认

`runtime/command_channel.py` 维护唯一在途命令。新版 ActionRecorder 宣告
`recorder_command_protocol=1` 后，controller 在原始 CommunicationMod 命令外包装
指令 ID 和前状态 ID；游戏端校验当前状态再调用官方 CommandExecutor。
这对模型、教师、人工及自动动作使用相同的提交路径。只有匹配的正常回执才能确认 pending；
Recorder 的 before/execution/settled 快照、旧状态和其他指令的错误不会确认当前动作。
出牌/结束回合如果仍处于 queued pending，继续等待实际执行结果；取消/跳过按失败记录。
等待超过 60 秒或断开时停止，未确认动作记录为 `accepted=null, execution_status=unknown`，
不盲目重试。已记录的 `command_confirmation` 包含协议来源及回执。

回执的 accepted 表示官方命令提交成功，不表示画面动画全部完成；后状态的原有局限不变。
未安装新版 Recorder 时仍使用原始协议，但轨迹明确标为 `legacy_unverified`，
不能把它当成有指令 ID 的执行证明。协议字段不进入模型提示词或动作别名。

Recorder 同时监听官方出牌接口真正加入 CardQueueItem 的位置和药水实际 use/discard 的位置，
因此接口操作和鼠标操作均能进入原始轨迹；队列条目按对象身份去重，不能按牌名合并。
词条说明来自实际 card.keywords 或实体关联 tooltip；不再按名称和正文猜匹配。
