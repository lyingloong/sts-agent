# arXiv 论文计划（工作稿）

更新：2026-10-27。本文是规划，不是结果。所有数字要么标注来源，要么标注为估算。

## 0. 一句话判断

工程骨架和数据管线已经够发一篇论文了，但**现在既没有可训练的人类数据，也没有任何 SFT 结果**。
距离"相对完整、可以挂 arXiv"的差距主要不在代码，而在三件事：数据规模与多样性、与零样本基线的
同口径对照、以及一个审稿人认可的研究问题。按当前投入强度，8–12 周是现实区间。

## 1. 现状盘点

| 资产 | 现状 | 论文需要的缺口 |
| --- | --- | --- |
| ActionRecorder | 0.1.6，协议 0.5，可实机采集 | 长跑稳定性统计（连续 N 局无人工修复） |
| sts-agent | 采集/推理/评测/导出全链路可用，493 项离线测试 | SFT 检查点、批量评测的统计口径 |
| 人类数据 | **0 局**（旧数据已按质量清理） | 150–300 个完整胜局，最好 ≥3 名玩家 |
| 零样本基线 | Qwen3.8-27B BF16，10 个固定种子，进度分 27.33 ± 13.07，通关率 0 | 更多种子、同尺寸（8B）对照、置信区间 |
| 评测口径 | Orak 风格进度分 + 通关率 + 幕通过率 | 种子族留出、bootstrap CI、成本/延迟表 |
| 训练 | QLoRA 管线与切分逻辑已有 | 8B 实际训练、超参、数据量曲线 |
| 分析 | 有单局人工复核经验 | 系统化错误分类、信息通道消融 |
| 发布物 | 两个 MIT 仓库 | 数据集卡、许可论证、CITATION、复现脚本 |

已经能写进论文的硬事实：一套可审计的细粒度采集协议；一个覆盖全部房间类型的完整对局 agent；
一个在 10 个种子上跑通的零样本基线；以及"信息给全了模型仍会决策错"这类观察。

## 2. 论文定位

三个可选方向，建议以 C 打底，B 作为加分项而不是主线。

- **A. 数据集 + 基准论文**：人类细粒度决策数据集 + 固定种子评测协议 + 若干基线。
  风险最低，但需要数据规模和发布许可都站得住。
- **B. 方法论文**：隐式推理 / 教师特权信息蒸馏 / 事后归因 RL。想法新，但需要对照组、
  更多算力和更强的理论动机；当前连 baseline 都还没有，不适合作为第一篇的主线。
- **C. 混合（推荐）**：把 A 作为主体，附上一节受控分析回答"信息 vs 能力"的问题。
  这样即使 SFT 模型打不过 27B 零样本，论文仍然成立。

### 研究问题

- **RQ1（迁移）**：动作级、细粒度的人类监督，能否迁移到跨房间类型的全流程自主游玩？
  度量：同尺寸模型 SFT 前后在留出种子上的进度分与通关率。
- **RQ2（信息 vs 规模）**：在固定模型下，状态信息通道（房间历史、运行时描述、牌堆明细）
  与模型规模，哪个对长程表现贡献更大？度量：消融矩阵。
- **RQ3（失败模式）**：LLM 在长程随机游戏中的失败是否主要来自信息缺失，还是来自决策?
  度量：错误分类 + 信息充足性对照。

### 明确不做的 claim

- 不说"首个 StS agent"（Orak、SpireBench、AscensionAI、sts_ml 都在）。
- 不说"大规模通用数据集"（单人、单角色、A0）。
- 不把 3–10 局的方差当成策略结论。
- 不声称通关率能与其他论文的分数直接横比（口径不同）。

## 3. 数据

### 3.1 规模目标

沿用 2026-10-01 的估计，按"独立胜局数"计：

| 完整胜局 | 能得到什么 |
| --- | --- |
| 30–50 | 打通采集→导出→训练→自主游玩链路，暴露动作与提示词缺陷 |
| 150–300 | 第一版有意义的 A0 战士 SFT，可能偶尔通关 |
| 500–1000 | 才有资格谈稳定表现，且仍无保证 |

论文主张建议定在 **≥150 个胜局**；若只能到 100 左右，就把贡献表述为"pilot 数据集 + 基准"，
不要用"large-scale"。

### 3.2 采集设计

- **种子独立**：每局不同种子，禁止同一局多次导出当多条数据。
- **玩家多样性**：≥3 名玩家（含作者）各贡献一部分；单人数据必须在 limitations 里点名，
  并报告玩家间动作分布差异。这是审稿人最容易攻击的点之一。
- **范围**：主集 Ironclad A0；可加 10–20 局 A5/A10 作为泛化性附录，但不进主训练集。
- **元数据**：游戏版本、ModTheSpire/BaseMod/CommunicationMod/ActionRecorder 版本、语言、
  采集日期、玩家编号、是否读档、终局类型。
- **负面样本**：死亡局也保留，用于错误分析和"胜局筛选是否有偏"的讨论，但不进 SFT 主集。

### 3.3 质量门槛

采集验收清单之外的量化门槛，建议写进论文：

- `usable_for_sft=true` 的决策占全部决策的比例（当前链路应 ≥95%，否则先修链路）。
- 排除原因分布（未匹配、取消、缺前置状态、读档段）。
- 动作与合法动作表的一致率必须 100%（不一致即数据错误，不是模型错误）。
- 每局决策数分布、token 长度分布（P50/P95/max）。

### 3.4 发布与 IP（必须先想清楚）

游戏文本（卡牌/遗物/事件描述）是 MegaCrit 的版权内容。直接把带描述的完整状态发到 HuggingFace
有风险。三个方案：

1. **全文本发布**：最好用，法律风险最高。
2. **结构化状态 + 本地渲染器（推荐）**：发布实体 id、数值、动作、种子、结局和渲染代码；
   使用者在拥有游戏的前提下本地重建文本。可复现，且不复制受版权保护的文案。
3. **仅动作序列 + 种子 + 结局**：最安全，但对训练复现不够。

建议默认方案 2，并在论文里说明"文本由本地游戏客户端重建"。数据集卡里写清许可、
出处、以及不包含游戏资源。

## 4. 模型与训练

### 4.1 实验矩阵（最小可用版）

| 编号 | 模型 | 数据 | 用途 |
| --- | --- | --- | --- |
| B0 | Qwen3-8B 零样本 | — | 同尺寸对照，最关键 |
| B1 | Qwen3.8-27B 零样本 | — | 已有 10 种子结果，扩到 30 |
| S1 | Qwen3-8B QLoRA | 150 胜局，canonical | 主结果 |
| S2 | Qwen3-8B QLoRA | 150 胜局，三布局轮换 | 格式鲁棒性消融 |
| S3 | Qwen3-8B QLoRA | 50 / 100 / 150 胜局 | 数据量曲线 |
| S4 | Qwen3-8B QLoRA | 150 胜局，去房间历史 | 信息消融 |
| S5 | Qwen3-8B QLoRA | 150 胜局，去运行时描述 | 信息消融 |
| S6 | Qwen3-0.6B / 4B | 150 胜局 | 规模消融 |

算力上，8B QLoRA 单卡 4090 可跑；150 胜局约 6 万条样本、每条约 2.4k token，
2–3 个 epoch 大致是几十 GPU 小时量级（估算，需实测）。

### 4.2 训练要点

- 按种子族切分，验证集固定 canonical 布局；不要随机切动作。
- 只对答案 alias 与结束标记算 loss，输入不计 loss。
- 记录每次训练的 manifest（数据哈希、超参、token 统计），论文附录直接引用。
- 先跑 0.6B 冒烟，再上 8B；不要一上来调 8B 超参。

## 5. 评测

- **种子集**：20–30 个留出种子（与训练集的种子族不重叠），每种子 1 局（种子确定，重复跑
  只用于估计技术噪声）。
- **指标**：进度分均值 ± bootstrap 95% CI、通关率、各幕通过率、非法动作率、卡死/技术中断率、
  人工接管次数、p50/p95 延迟、每次决策 token 数。
- **人类参考**：同一批种子上采集者的胜率，作为上界参考而非对比基线。
- **成本**：10 局约 2 小时墙钟、6.3M prompt token。30 局 ≈ 6 小时/配置；8 个配置 ≈ 50 小时，
  这是除采集外的第二大时间开销，需要提前排期。
- **报告纪律**：n、种子、版本、失败原因全部写进表；技术中断不计为死亡。

## 6. 分析（论文的"厚度"来源）

1. **错误分类**：从日志自动检测 + 人工抽样标注。建议类别：非法/无效动作、重复循环、
   漏杀、药水误用、路线/经济决策、对敌方 buff 的忽视、读牌堆错误。
2. **死亡分布**：按幕、按遭遇、按死因；对比人类同种子死亡点。
3. **信息通道消融**：S1 vs S4/S5，直接回答 RQ2。
4. **信息充分性 vs 策略能力**：像守护者"锋利外壳"那样，信息完整但决策顺序错误的案例，
   是最有说服力的定性证据，建议做 3–5 个 case study。
5. **数据效率**：S3 曲线，回答"多少人类数据才够"。

## 7. 人力与时间（最大风险）

单局 A0 战士按 45–90 分钟、胜率按 50% 估：

- 150 胜局 ≈ 300 次尝试 ≈ **225–450 小时**游戏时间；
- 300 胜局 ≈ 600 次尝试 ≈ **450–900 小时**。

单人兼职做不完。可行的缓解，按推荐顺序：

1. **3 名玩家轮换**，把墙钟压到 1/3；同时天然满足"多演示者"要求。
2. **降低规模到 100–150 胜局**，把主张改成 pilot + benchmark。
3. **众包/招募**（需要采集协议、知情同意和数据许可说明）。
4. **AI 轨迹补充**：Codex 接管模式可以量产轨迹，但历史经验是水平一般、成本不低；
   只能作为辅助数据或另一条对照臂，不能冒充人类专家数据。

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 采集工时不足 | 主张降级 | 多人采集；先做 50 局拿初步曲线 |
| SFT 打不过 27B 零样本 | 主结果弱 | 同尺寸对照 + 数据效率叙事 + 失败分析 |
| 单人数据 | 泛化性质疑 | 多玩家；limitations 明说 |
| 游戏文本版权 | 数据集无法发布 | 结构化状态 + 渲染器 |
| 评测方差大 | 结论不可信 | 20–30 种子 + CI + 原始日志公开 |
| 算力/环境 | 训练延期 | 先 0.6B/4B 跑通，再排队 8B |
| 版本漂移 | 不可复现 | 固定游戏/Mod/模型版本，写进 manifest |

## 9. 论文骨架

1. Introduction：长程游戏为什么难；现有工作只覆盖局部（Orak 只做战斗与选牌，SpireBench 是
   STS2 + 文件 IPC）；我们的完整对局设定与贡献。
2. Related work：LLM game agents、StS 相关系统与数据集、行为克隆/DAgger、benchmark 设计。
3. System：采集 Mod、agent 框架、状态/动作契约、评测协议。
4. Dataset：规模、采集流程、质量门槛、统计、许可。
5. Baselines & Method：零样本、SFT 配置、prompt 布局。
6. Experiments：主表、数据量曲线、消融。
7. Analysis：错误分类、case study、信息 vs 能力。
8. Limitations & Ethics：单角色/A0/单游戏、版权、演示者数量。
9. Release：代码、数据、适配器、复现命令。
